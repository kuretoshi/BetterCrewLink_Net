# Official TanukiBCL v3.2.7 interoperability checkpoint (2026-10-02)

The official `v3.2.7` Windows release was downloaded, checked against the SHA-512 in `latest.yml`, extracted without running the installer, and launched with an isolated user-data directory. It joined the existing Airship lobby `ETQYMR` as Among Us client `3937`. The .NET probe joined as client `3938`.

Run the focused test with `--tanuki-interop-test --game-process-id 60232 --expected-peer-client-id 3937 --seconds 30`. The expected-client filter is important: an earlier unfiltered test passed by connecting to a different vDEV client. The focused test now passes against the official release: WebRTC reached `connected`, the data channel exchanged a NoS radio payload, 30 Opus test-tone frames were sent, and PCM frames were received from that same client. This verifies transport and audio frames, not yet subjective audible quality in the official GUI.

The initial failure was a glare race: both peers offered concurrently and an already superseded connection could still receive data while the active connection could not send audio. The .NET side now follows the upstream offer tie-break more closely, does not create a peer from an orphan candidate or answer, and treats received data as evidence that the channel is usable even when SIPSorcery has not fired `onopen`. ICE uses `relay` only when the voice server explicitly requests it, matching upstream 3.2.7.

The two-client .NET self-test also passes after these changes. Remaining work includes audible bidirectional testing, reconnection under churn, the rest of the 3.2.7 game/audio policies, GUI parity, and packaging. This checkpoint is not a compatibility-complete claim.

The .NET Audio settings expose the 3.2.7 microphone-sensitivity slider and enable switch. The VAD now follows the upstream 1024-sample Blackman-window analyser, 85–255 Hz frequency-band average, 0.2 spectral smoothing, Web Audio byte/dB scaling, and 0–30 activity counter. A deterministic synthetic-audio test checks speech-band start, silence stop, out-of-band rejection, and sensitivity behavior. Live comparison with the official Electron app is still needed; device capture, browser processing timing, and platform audio effects may differ.

The official audio settings' crew-as-ghost and ghost-as-impostor volume sliders are now exposed in the .NET settings UI with the 3.2.7 defaults (100% and 10%). The ghost listener multiplier applies to proximity, meetings, and radio, matching the upstream post-policy peer gain. Policy self-tests cover those cases. Audible comparison with the official app is still pending.

The three upstream microphone activation modes (voice activity, push-to-talk, push-to-mute) and four default single-key shortcuts are now represented in local settings. A narrow Windows key-state monitor polls only the configured keys while the client is running; it is suspended while the settings dialog captures a new binding. Audio is gated by the selected mode and manual mute, and the local VAD status reflects transmitted speech. The synthetic-audio self-test checks mode truth tables. A live Among Us foreground-key test and comparison to the official app are still required.

At 15:18 JST, a fresh focused interop run against official client `3937` again reached `connected`, exchanged a data-channel radio payload, sent 30 Opus tone frames, and received PCM from the same peer. This regression check used the existing probe executable; it does not exercise the new WPF hotkey monitor. The Windows UI automation helper failed twice to bind the already-running WPF window (it returned an unrelated Oculus app identifier for a window titled `TanukiBCL`). After the user closed Oculus, the exact .NET client process was closed, rebuilt, and relaunched as PID `59272`; it has a responsive `TanukiBCL` main window, but the helper still assigned that new window to the Oculus app identifier and refused to bind it. No GUI input was attempted after this repeated identification error. Foreground-key verification still requires a working UI binding or user-operated test.

Vent-received proximity audio now carries the upstream 2 kHz, Q=20 low-pass muffle before panning; an otherwise-unmodified gain is reduced to 50%. Meeting audio bypasses this effect. Radio audio normally uses the upstream 1 kHz, Q=10 high-pass and a 90 ms echo (92% dry, 20% wet, 12% feedback). In tasks, a living participant in a vent overrides the radio high-pass with the vent low-pass and halves the unmodified gain, while keeping the echo. Policy, synthetic-frequency, and impulse-response tests verify these routes and coefficients. Audible A/B comparison with the official 3.2.7 binary is still pending.

After the user closed the Oculus screen, the Windows UI helper still returned the WPF `TanukiBCL` window under the Oculus app identifier and failed to capture it. We stopped UI input rather than targeting an uncertain window. The new radio effects passed the policy/VAD self-tests and a zero-warning WPF build in an alternate output directory. At 15:56 JST, the focused official-client interop probe again reached WebRTC `connected`, exchanged the NoS radio data-channel payload, sent 30 Opus tone frames, and received PCM from official client `3937`. This proves transport regression only; the running WPF process has not been replaced with the newly built effects and live listening is still outstanding.

The subsequent UI retry attempted to bring the one returned WPF-titled window to the foreground, but the helper rejected that activation before changing focus: it reported the window under an Oculus app identifier, while separately listing the actual `TanukiBCL.Client` process with no windows. A second user-requested Oculus close did not change that classification. This is an app/window identity failure in the helper, not evidence that the WPF app itself has closed.

The Web Audio specification states that low-pass and high-pass `BiquadFilterNode.Q` is expressed in dB and uses the linear equivalent `10^(Q/20)`. The initial .NET vent and radio filters had incorrectly passed the upstream dB values directly to NAudio's linear-Q biquad. They now convert 20 dB to 10 for the vent low-pass and 10 dB to approximately 3.162 for the radio high-pass. Camera reception from `spatialAudio.ts` is now implemented for the Airship, Polus, and Skeld camera coordinates from `AmongusMap.ts`: when a speaker is beyond normal range but near the selected camera, it uses camera-relative attenuation/panning, 80% unmodified gain, and a 2.3 kHz low-pass with -15 dB Q. Policy and synthetic-frequency tests pass, as does a zero-warning WPF build. Live audible A/B verification remains outstanding.

The `wallsBlockAudio` policy now uses the exact v3.2.7 `ColliderMap.ts` wall and closed-door path data, embedded as JSON. Its SVG paths are parsed once; cubic curves are subdivided to 0.001 map-unit flatness before segment intersection. Normal task proximity is blocked for living listeners, while meetings, radio, ghosts, and camera reception follow the upstream exceptions. The memory reader's door cap was raised from 16 to 64 so Airship door IDs 16-20 can be observed. Self-tests cover Fungle walls, Skeld and Airship doors, the mirrored April Skeld, and policy exceptions; the WPF build is warning-free. The subdivision is a close numerical port of `path-intersection`, not yet a proof of identical behavior at every curve boundary. Live game testing with the lobby option enabled is outstanding.

We did not send UI input through that misidentified handle.
