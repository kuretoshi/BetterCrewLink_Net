# 設定の即時反映とNoSロビー検証（2026-10-03）

比較基準はTanukiBCL v3.2.7、コミット `9861ccc8137bb63a7d3834f493be0b784a288544`。完全移植の完了記録ではない。

## 実装

- 設定画面の一括保存・キャンセルを廃止。変更イベントをメイン画面、音声設定、表示へ即時反映する。
- 通常スライダーは操作中に実行時値を反映し、操作終了で対象キーのみ保存する。他のチェックボックス操作では未確定スライダー値を保存しない。
- マイク感度は操作終了時のみ反映。3.2.7と同じ条件の感度警告、NAT有効化、幽霊のみ・会議のみ設定の確認を追加。
- 自分のロビー設定は750ms後に保存し、画面切替・非アクティブ化・終了時に未反映の変更を反映。ホストのゲーム中編集制限と現在のロビー設定の読み取り専用表示を維持。
- 音声デバイス、AEC/NS/AGC、サーバー変更時はセッションを再生成。終了待ち中の連続変更をまとめ、最新設定で再開する。明示的な停止を優先し、ミュート・スピーカーミュートを保持する。
- 保存失敗時はエラーを表示し、通常設定の失敗キーを終了時に再試行する。

## 検証と制限

Releaseビルドは警告・エラー0件。設定トランザクション、実WPFコントロールイベント、750msタイマー、確認ダイアログ、保存失敗、再起動の集約、ライフサイクル、オーバーレイ、入力処理の自己テストを実行した。

自己テスト中のWPFウィンドウ終了でテスト全体が早期終了し得た問題も修正した。テストモードでは `OnExplicitShutdown` を使用し、故意の例外を起こす `--settings-self-test --self-test-failure-exit` が終了コード1になることを配布物で確認した。修正前の終了コード0のみを完全な検証証拠にはしない。

`publish/live-settings-20261003` の実行ファイルを起動。NoS 3.5.1の既存4プロセスでAirshipの非公開ロビーを作成し、全員参加を画面で確認した。新しい.NET実行ファイルにWindowsのネットワーク許可ダイアログが出たため、その先の通信・実GUI設定変更試験はユーザーの許可操作待ち。ダイアログを自動操作していない。

NoSの追加スナップショット読取はTasks/Discussion中に開始するため、ロビー中の未取得表示だけでは読取障害と判定できない。

従来の `--scan-game` は5プロセス固定かつTasks/Discussionしか受理しなかった。`--expected-players`（既定5）を追加し、明示したLobbyも受理するよう修正。読取結果が空または一部欠落した場合に音声ルールだけPASSになる誤判定も修正した。回帰テスト `--game-scan-self-test` は人数不一致、生存人数不一致、異なるロビー、読取欠落、空結果、引数を検査する。

次の実機コマンドは終了コード0。4プロセスすべて同じロビー、4人生存・死亡0、ローカルclient IDの重複なしを確認した。これはメモリ状態と音声ポリシーの確認であり、実際に音声が届く証拠ではない。

```powershell
dotnet src/TanukiBCL.VoiceProbe/bin/Release/net8.0/TanukiBCL.VoiceProbe.dll --scan-game --expected-game-state Lobby --expected-players 4 --expected-alive 4 --expected-dead 0
```

GUIの完全一致、残りの設定項目・更新機能、MOD役職の実ゲーム検証、実音声効果と相互運用の全シナリオは引き続き未完。
